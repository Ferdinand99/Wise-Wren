# Wise Wren – Phase 6 API + MCP, hardening, docs, site and templates (v0.1) implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
> Each task is test-first: write the test named under **Proof**, see it fail, then make it pass.

**Goal:** Wren is ready for its first release, v0.1.0 (design §12, phase 6): REST v1 and MCP cover what the web UI
does (design §9), the server-side fetches and the agent channel are hardened (design §8), and there is a real
install path (README, user guides, site, Unraid templates for the server and the agent). Nothing is released:
release PR #4 stays open until the owner has tested.

**Architecture:** no new moving parts. The REST additions reuse the functions the pages already call (servers,
registries, Vigilant Vole, monitor links, intervals, "Check now", rollback, notification channels); the page
handlers keep their HTML answers. MCP gets tools for the operational actions; anything that would put a secret in
an assistant's context (agent tokens, registry passwords, the VV token, channel secrets) is REST only. Server-side
fetches of user-influenced URLs go through one guard (`src/fetch.rs`).

**Spec:** `docs/design.md` §2 (anti-goals), §8, §9, §11, §12.

## File structure

```
src/fetch.rs        # the guarded fetch: public addresses only, pinned DNS, per-hop redirects, size/time caps
src/api_settings.rs # REST + MCP helpers for servers, registries, Vigilant Vole, notification channels
src/api.rs          # target/run additions (get, check, interval, resume, rollback, monitor links), docs, MCP
src/versions.rs     # URL version sources through fetch.rs; GitHub release links kept only on github.com
src/registry.rs     # credentials only to an https token realm (or the registry's own host)
src/runs.rs         # the job long-poll re-checks the token before it hands out a job
agent/src/jobs.rs   # paths with `..` never count as under a root
docs/*.md           # user guides; README install; site/; unraid-templates (server + agent)
```

## Global constraints

- **Roles:** viewers read; editors approve, schedule, skip/snooze/resume, cancel, roll back, Check now, intervals,
  notification channels; admins add/delete servers and agent tokens, registries, the Vigilant Vole connection and
  monitor links, and turn automatic updates on. Same rules as the pages.
- **Writes need a write API token** (`AuthMethod::Token` with a write scope). A session cookie on any
  `/api/v1` write is refused with 403 (those paths are CSRF-exempt, so a cookie must never be enough).
- **Secrets never leave sealed:** agent tokens are shown once (REST answer to add/new token only), registry
  passwords, the VV token and channel secrets are write-only (`has_password`, `token_saved`, redacted configs).
- **No new remote powers:** nothing added lets Wren send a command line or a path to an agent.

## Review Focus

1. **SSRF guard** (`fetch::get_limited`): every address of the host is checked (IPv4 and IPv6: loopback, private,
   link-local, CGNAT, multicast, unspecified, broadcast, documentation, benchmarking, ULA, site-local, and IPv4
   inside IPv6: mapped, compatible, NAT64, 6to4); the connection is pinned to the checked address
   (`ClientBuilder::resolve`, no proxy); redirects are followed by hand, at most 3, each hop checked again; body
   capped at 256 KiB while streaming; 20 s for the whole fetch; only the extracted version is stored.
2. **Agent tokens:** SHA-256 at rest, looked up by hash (no comparison of secrets in memory), checked on every
   request, also again before a long-poll hands out a job, so revocation takes effect at once.
3. **Cookie refusal and CSRF:** every new `/api/v1` write goes through `writer`; pages keep the kit's CSRF guard.
4. **Secrets in answers and logs:** REST/MCP JSON never carries a stored secret; no log line carries a token, a
   password or a URL's user info.
5. **Credentials to the right place:** registry credentials are sent to a token realm only over https or on the
   registry's own host.
