Up to date.
Without surprises.

Wise Wren keeps the Docker containers on your servers up to date. It checks for new versions on a schedule you choose, tells you about them, and updates only what you approve. Every update gets a snapshot first, a health check after, and a rollback if it fails.

Wren never changes anything you haven’t allowed.

Updates shouldn’t be a daily chore.

Keeping a home server current means checking every container, every day, and hoping each update goes well. Wren is being built to do the checking, ask before it acts, and clean up after itself when something breaks.

  • A manual check, every day

    Open the Unraid web UI, look for updates, press the button, check it came back. Nothing tells you when a new version is out.

  • The button doesn’t cover it all

    Unraid’s update button handles containers made from its templates. Compose stacks and stacks updated by a vendor’s own script are left to you.

  • Other tools pick an extreme

    Some only notify, like Diun and What’s Up Docker. Others update blindly, like Watchtower. None of them pause your monitoring, take a snapshot, check health and roll back.

Wren never changes anything you haven’t allowed. With automatic updates off, which is the default, Wren updates nothing on its own: not a container, not a stack, not a “small” dependency. A production server updated behind your back is the worst outcome, so Wren is designed around avoiding it.

Safe updates

Every update, the same careful steps.

Whether you press the button, schedule it for tonight or let it run on its own, an update will go through the same steps, and each one is written to the target’s history.

  1. 1

    Preflight

    The server is reachable, there’s room for a snapshot, and the new image is pulled before anything stops.

  2. 2

    Maintenance window

    A window opens in Vigilant Vole for the linked monitors, so a planned restart doesn’t alert anyone.

  3. 3

    Stop

    The container or stack is stopped gracefully, so its databases are consistent.

  4. 4

    Snapshot

    The service’s data is saved as a local rollback point. If there isn’t room, the update is refused rather than filling the disk.

  5. 5

    Update

    Pull and recreate the container, bring the Compose stack up again, or run the vendor’s update script.

  6. 6

    Health check

    The containers are running and healthy, and the linked monitors stay up for a stable few minutes.

  7. 7

    Roll back if it fails

    The previous image or Compose files and the snapshot come back, and the health check runs again. If even that fails, Wren stops and tells you it needs you.

    Only on failure
  8. 8

    Close and report

    The maintenance window closes, and you get one notification with the result.

Nothing waits forever Every step has a time limit, and a run can be cancelled until the moment the service is stopped.

Snapshots are not backups They are short-lived rollback points on the same server, kept only while there’s room. Your own backups stay your offsite copy.

Modes and schedules

You decide how much Wren may do.

Each server has a default mode, and each container or stack can override it. Checking for new versions never changes anything; only updating does.

  • Notify only

    Wren tells you a new version is out, with release notes when it can find them. Nothing else happens.

  • Default

    Approve

    One click runs the update now, or at a time you choose. You can also skip a version or snooze it. An approval is for that one version, never the next.

  • Off unless you turn it on

    Automatic

    Updates run on their own, but only inside a window you set, such as 03:00 to 05:00 at night. Any container or stack can be excluded.

Approve now, update tonight.

Approve an update during the day and pick when it runs. A scheduled update shows up as planned maintenance in Vigilant Vole ahead of time, so the people who use the service can see it coming.

Wren checks for new versions on an interval you choose for each server, every six hours unless you say otherwise, and sends one notification per new version, with a digest if you prefer. Notifications go through the same ~40 channels as the rest of the family, from ntfy on your phone to email and Discord.

What it updates

Three kinds of targets.

A target is one thing Wren updates as a unit. Containers and Compose stacks are found on their own; script stacks you add by hand.

  • Containers

    Single containers, including the ones Unraid creates from its templates. The aim is to recreate those the way Unraid does, so its web UI stays in step.

    New version: the image in the registry has changed, or a newer tag matches the range you follow.

  • Compose stacks

    Docker Compose projects, found from Compose’s own labels. The stack is pulled and brought up again as one unit.

    New version: any of the stack’s images has changed.

  • Script stacks

    Apps such as Fluxer that update with the vendor’s own installer. Wren runs a script you defined on that server, and only by name.

    New version: a source such as GitHub releases reports a newer version than the one installed.

One Wren, several servers.

One central Wren keeps the list, the policies and the history. A small agent on each server does the work there.

The agents connect out to Wren, so your servers open no ports, and they only run scripts defined in their own local config. Wren is designed so that it can never become a remote shell on your servers.

Better together

Works with Vigilant Vole.

Wren and Vigilant Vole are siblings. Connect them, and an update stops looking like an outage.

  • A maintenance window opens before anything stops, so a planned restart doesn’t page you.
  • A scheduled update shows as planned maintenance on your status pages ahead of time.
  • Your monitors become part of the health check: the service has to stay up for a few minutes before the update counts as done.
  • Without Vigilant Vole, Wren checks the containers themselves, and says so.

Try it on your own servers.

v0.1 is an early release: two Docker images for amd64 and arm64, the server (ghcr.io/ferdinand99/wise-wren) and the agent for each Docker host (ghcr.io/ferdinand99/wise-wren-agent). It is tested on Unraid; other Linux hosts with Docker are best-effort for now.

  1. Start the server and open http://<host>:3003/setup to create the first admin.
  2. Servers → Add server shows the agent’s token once, with the docker run line for that host.
  3. Start the agent. On Unraid, use the Wise Wren and Wise Wren Agent templates from Community Applications.
  4. Limit what the agent may update with [updates] in its agent.toml, then approve your first update.

The agent uses the Docker socket, which is root on its host. Wren’s snapshots are rollback points, not backups. Read the guides: install, agents, updates, snapshots, Vigilant Vole and security.

An agent’s agent.toml 
# Folders Wren may touch, mounted at the same path
roots = ["/mnt/user/appdata", "/mnt/cache/appdata"]

# Only these may ever be updated, whatever Wren asks
[updates]
allow = ["nextcloud", "immich"]
deny = ["*-db"]

Where it stands.

Wren is built in phases, riskiest part first, and v0.1 is the first release. There are no dates: each step is done when it works, and the phase table in the design says what “works” means.

  1. Done

    Design and spike

    Goals, anti-goals and the safe update flow, then a throwaway test of the risky parts on a real Unraid server: template containers, a vendor’s update script, snapshots and registry checks.

  2. Done

    Skeleton on vole-kit

    Sign-in, users, settings and 26 languages from the family’s shared foundation, and servers with agents that show as online.

  3. Done

    Finding versions

    Containers, Unraid templates, Compose stacks and script stacks, with release notes and one notification per new version.

  4. Done

    Safe update runs

    Approvals, snapshots, health checks, rollback and history: a deliberately broken update rolls back on its own.

  5. Done

    Vigilant Vole and schedules

    Maintenance windows, planned maintenance, health checks from your monitors, and automatic mode with windows and exclusions.

  6. Early release

    v0.1

    The REST API and MCP tools for everything the web UI does, hardening, user guides and Unraid templates for the server and the agent. Docker images only.

  7. Then

    v1.0

    Static binaries and a Linux installer, more testing on other Linux hosts and filesystems (btrfs subvolumes, ZFS), and reviewed translations.

Later: an iOS app to see available updates and approve them, with push notifications, built on the REST API that already covers everything the web UI does.

Questions.

  • When can I use it?

    Now, as an early release. v0.1 is a Docker image for the server and one for the agent; Install shows how to start, and Unraid templates for both are in unraid-templates. Static binaries and an installer come by v1.0. Watch or star the repository to hear about new releases.

  • Is it open source?

    Yes, under the MIT license, like Vigilant Vole, Nimble Newt and Keen Kestrel. No paid tier, no account.

  • Does it work outside Unraid?

    Yes, best-effort for now. Wren is tested on Unraid, where its maker runs his own containers, including the ones Unraid creates from its templates. Plain containers and Compose stacks on other Linux servers with Docker work too, with plain-copy snapshots on filesystems without reflinks; they get more testing before v1.0.

  • Will it ever update without asking?

    No, unless you turn on automatic updates for that container or stack. Automatic mode is off by default for every server and every target.

    Even when it’s on, updates only run inside the window you set, and you can exclude anything you’d rather update yourself. In approve mode, an approval covers one version: if a newer one appears before the update runs, Wren asks again.

  • Will there be an iOS app?

    Yes, later. It is planned after v1: an app to see available updates and approve them, with push notifications. Until then, notifications reach your phone through ntfy or any of the other channels.

  • Is it a backup tool?

    No. Wren’s snapshots are short-lived rollback points on the same server, there to undo one update. Keep your own backups, ideally somewhere else.

  • How can I help?

    Try the early release and open an issue with what breaks or surprises you. Reports from Linux hosts other than Unraid, and from btrfs subvolumes or ZFS, are especially welcome.
